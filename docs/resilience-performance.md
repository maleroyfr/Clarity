# Resilience and large-volume performance

Pilot-readiness evidence for worker restarts, throttling and a forest of about
50,000 users and 500,000 relationships. Every figure below comes from synthetic,
anonymized data generated by `SyntheticDossier` on a disposable SQL Server; no
customer tenant or export was used. A real pilot tenant can differ in shape (deeper
nesting, more attributes, more sections) and must be measured during the
user-led pilot.

## Restarts, lease loss and throttling

Background work runs as `CollectionJobs` claimed from SQL by a lease
(`SqlJobQueue`):

- a claim sets a 45-second lease and a new lease token; the worker heartbeat
  renews it while the handler runs;
- a host interruption leaves the lease to expire; another worker reclaims the job
  with a new token and the next attempt number;
- retryable failures (`RetryableCollectionException`, SQL deadlock 1205 or
  timeout) are re-queued after `2^attempt × 5` seconds, up to 3 attempts; others
  fail with a stable error code;
- handlers that record results take an `UPDLOCK, HOLDLOCK` read of the job row in
  the transaction of their final save (`SqlJobQueue.FenceAsync`) and abandon with
  `CancelledOrLeaseLost` when their token, state or lease is no longer current.

Microsoft Graph calls (`GraphTransport`) retry 429, 502, 503 and 504 three times,
honouring `Retry-After` up to 60 seconds, otherwise waiting 1, 2 and 4 seconds.
A longer `Retry-After` fails at once with `RetryAfterLimit`; exhausted retries
fail with `Throttled`. The section then stays failed with the earlier published
observations visible, and the consultant relaunches it. Azure Blob calls use the
Azure SDK default retry policy; this is not exercised by tests.

| Situation | Behaviour | Evidence |
|---|---|---|
| Worker stops after a section is published | The reclaimed attempt resumes without duplicate observations or objects | `JobTests.RestartDuringProcessingResumesPublishedSectionWithoutDuplicates` (R08) |
| Two workers claim, lease expires, stale worker completes | One claim wins; the reclaimed attempt owns the job; stale renew and completion are ignored | `JobTests.CompetingClaimsLeaseExpiryAndStaleCompletionAreFenced` |
| Graph collection interrupted | The delta cursor is persisted only after publication; the restart publishes once | `GraphTests.GraphUsesCommonIngestionSurvivesRestartAndPersistsCursorOnlyAfterPublication` (R03, R08) |
| Graph 503 or 429 | Bounded retries with 1, 2, 4 s back-off; long `Retry-After` is not retried early | `GraphTests.RetriesAreBoundedAndLongRetryAfterDoesNotRetryEarly`; `GraphTests.PagingThrottleAndDeltaReplayPreserveAbsentAndExplicitEmptyFields` |
| Repeated throttling of a job | Three attempts, then `Failed` with `Throttled`; retry and cancel stay authorized | `JobTests.BoundedRetryCancellationAndMembershipRevocationArePersisted` |
| Report download retried after authorization change | Re-authorized at job time; the retry publishes exactly once | `ReportImportTests.JobTimeAuthorizationIsRecheckedAndRetryPublishesTheReportExactlyOnce` (R08) |
| Export worker loses its lease while writing files | The stale worker fails at the fence and deletes only its own files; the owner purges files of interrupted attempts and records its own | `ResilienceTests.ReclaimedExportRecordsOnlyTheLeaseOwnersFilesAndPurgesInterruptedAttempts` (R08, R14) |
| Decision changed while an export reads | `SelectionSuperseded`, no artifact and no file of mixed dates | `ResilienceTests.DecisionChangedWhileReadingSupersedesTheExportWithoutMixedDateFiles` (R14) |

### Export files under restarts

Export artifacts and `GeneratedAtUtc` are recorded together in one transaction, so
files of an attempt that never reached that transaction are never referenced. The
owning attempt, inside the fence, deletes every file under
`<workspace>/<export>/` except its own (`IExportStore.PurgeExportAsync`) before
recording. A stale attempt fails at the fence and deletes the files it wrote; it
can never delete the owner's files, because the purge only runs under the fence.

Residual risk: a stale worker that writes a file after the owner's purge and then
crashes before its own cleanup, or a hard kill on the last attempt, leaves an
unreferenced file. The retention sweep deletes such files after
`OrphanGraceHours`, and controlled deletion purges the whole export prefix
regardless of artifacts (see [retention and deletion](retention-deletion.md)).

## Volume run

`VolumeTests.ShardedForestAndTenantStayWithinPageAndBatchBudgets` collects one AD
forest as five domain shards of `CLARITY_TEST_VOLUME` users each, then the
matching Entra tenant, through the same staging, job and publication path as
consultant imports. With 10,000 users per shard:

- 50,000 AD users, 2,025 groups and 500,020 group memberships: each user belongs
  directly to one department group and nine of 400 project groups per shard, and
  the four department groups are nested in all-staff;
- 50,000 Entra users with hybrid anchors, matched to the AD users;
- one domain population per shard (about 10,000 objects, under the 20,000
  population limit) and an export of all 50,000 users (the 50,000-row limit).

It then times each consultant step: grid pages, sorts, filters and searches, the
object sheet, membership paths, mapping review, populations, scope decisions,
decision register, recomputation, scenario overview and export generation.
Interactive reads must finish within 5 seconds; population, scope, recomputation
and export operations within 3 minutes. Imports are reported without a budget,
with the time of each publication stage.

### Running it

```powershell
$env:CLARITY_TEST_SQL = "<connection string of a disposable SQL Server>"
$env:CLARITY_TEST_VOLUME = "10000"          # users per shard; 25 to 10,000
$env:CLARITY_VOLUME_REPORT = "$PWD\volume-report.md"
dotnet test --project tests/Clarity.Infrastructure.Tests --configuration Release --filter-trait "Category=Volume"
```

Without both variables the test is skipped. CI runs it on every push with 200
users per shard as a functional check. The `Volume` workflow runs the full size on
Mondays, on pushes to `ci/volume-**` branches and on demand
(`gh workflow run volume.yml -f users_per_shard=10000`); it publishes the report
in the run summary and as the `volume-report-<run>` artifact for 30 days.

to 20.2 seconds; observations stayed near 17 seconds. In the Entra import,
current values took 50.1 seconds, observations 33.0 seconds and hybrid matching
30.1 seconds. The full per-stage breakdown is in the run summary.

The previous full run,
[45988136060](https://github.com/maleroyfr/Clarity/actions/runs/45988136060),
failed its budgets on two reads: the UPN prefix search took 6,688 ms and the
transitive members of all-staff 12,538 ms. Both were fixed (see below) before
the run above.

### Tuning made for this volume

- **Observation keys.** Publication resolved each record's primary key with a
  tracked lookup, which re-scanned tracked entities per record. It now preloads
  the environment's primary keys once per section (ordinal comparison, matching the
  binary collation).
- **Relationship projection.** Each publication deleted and re-inserted every edge
  and support of the environment. It now computes the desired edges and applies
  only additions, changes and removals.
- **Grid paging.** The grid sorted and paged the full projection, including
  correlated subqueries, before taking 100 rows. It now pages identifiers first
  and projects only the selected page.
- **Index.** `ExternalKeys (WorkspaceId, ObjectId, IsPrimary)` including
  `Namespace` and `ExternalId` serves the primary key shown per grid row
  (migration `VolumeIndexes`).
- **Membership paths.** Transitive membership queries chose the From or To column
  inside the SQL predicate, which prevented index seeks; the direction is now
  chosen before the query is built.
- **Text search.** A search across name, UPN and other displayed keys used one
  predicate with several `LIKE 'term%'` alternatives, which SQL Server scanned.
  It is now a union of prefix seeks, one per indexed column (6,688 ms to 17 ms
  for a UPN prefix).
- **Transitive traversal.** Expanding members of all-staff queried the members of
  every reached object, including the 50,000 users that have none. The traversal
  now expands only objects that can contain members (12,538 ms to 275 ms).
- **Stage timing.** Publication stages emit `Clarity.Publication` activities
  (Observations, AlternateKeys, CurrentValues, DecisionReview, Relationships,
  Matching, Commit), visible in OpenTelemetry traces and in the volume report.

### Known limits at this volume

- Relationship projection and hybrid matching re-read all of an environment's
  relationship observations or identities on each publication; their cost grows
  with the environment, not only with the changed section.
- Imports and publications are serialized per environment by an application lock;
  a 10,000-user shard occupies its environment for the duration shown above.
- SQL commands use the default 30-second timeout; the environment lock waits up
  to 10 seconds.
- Package, population and export limits are unchanged: 16 MB compressed and
  128 MB uncompressed packages of at most 150,000 lines, populations of at most
  20,000 objects, exports of at most 50,000 rows, pages of at most 100 rows,
  comparisons of at most 200,000 objects per side.
